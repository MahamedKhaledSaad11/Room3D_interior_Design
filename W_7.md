## From Video to a Browsable 3D Room

Goal: a logged-in user (bonus / optional) uploads a video, watches a progress bar, and explores the reconstructed room in a free-camera 3D viewer in the browser.

## Objective:

By the end of the week, the following must work end to end:

- 1.Sign up and log in.

- 2.Create a project.

- 3.Upload a short room video.

- 4.Submit a “3D reconstruction” task.

- 5.See a progress bar with the current stage.

- 6.Open the result in a 3D viewer and move through the room with a free camera.

Editing is out of scope this week, but every artifact you produce (frames, poses, splat) must be stored in a form Week 2 can reuse. Treat that as a hard requirement.

## 2. Input Constraints (keep compute from exploding)

- Scene: a single room, slow camera motion, good lighting, no fast pans.

- Length: 2 – 5 minutes of video.

- Frames: extract 1–4 fps, based on capturing speed movements and overlapping between frames.

- Resolution: resize frames so the long side is 640–960 px. Never feed 4K or full- resolution frames to any model.

- Drop blurry frames, for example, with the variance of the Laplacian.


## 3. Roles

## Reconstruction Pipeline (ML)

- Frame extraction with ffmpeg (fps, resize, blur filter).

- Camera pose estimation with VGGT and/or GLOMAP. (vggt is faster but less accurate.)

- 3D Gaussian Splatting training and export.

## Backend and Job System

- projects/chats, uploads, task records, and status API.

- Worker that runs the reconstruction pipeline on the Kaggle notebook.

## Frontend and 3D Viewer

- Login/sign-up, project list, upload page, progress page.

- The in-browser splat viewer with free-camera navigation.

## 4. Technical Guidance

### 4.1 Pose estimation: VGGT vs GLOMAP (compare, then choose)

- VGGT is feed-forward. It gives camera poses, intrinsics, depth maps and point maps directly. It is fast but memory-hungry, because memory grows with the number of frames, and it can drift on long sequences. Research how to run it in chunks, in fp16, and how to merge chunks.

- GLOMAP is a global SfM method that works on a COLMAP database. The pipeline is feature extraction, then matching (use sequential matching for video), then the GLOMAP mapper, which outputs a COLMAP-format sparse model. It is slower to set up, but it is a well-understood baseline.

- Required experiment: run both on the same test video, then report the number of registered frames, runtime, peak VRAM, and a visual check of the point cloud. Choose one for the project and justify it in one paragraph.

- Whichever you choose, convert the output to a COLMAP-style folder (images/, sparse/0/cameras, images, points3D). Most 3DGS trainers expect this, and Week 2 depends on it.

- 3DGS assumes undistorted pinhole images. Check that your intrinsics are handled correctly.

### 4.2 Gaussian Splatting

- Research and pick a trainer. Two common options are the original reference implementation and the gsplat library. Check that it runs on T4 (CUDA compute 7.5).

- Start from the sparse point cloud produced above.

- Train for a modest number of iterations first (about 7k) to confirm the pipeline works, then a longer run (about 15–30k) for quality.

- Export a .ply, then convert it to whatever compact format your chosen web viewer needs (.splat, .ksplat, or similar).

- Log training time, final number of Gaussians, file size and peak VRAM.


### 4.3 Kaggle notebook architecture

- Structure the notebook as separate stage scripts (extract, poses, train, export) that run as separate processes, so VRAM is released after each one.

- Use a pull-based worker: the notebook polls the backend for pending tasks and uploads results back. This is more robust than exposing the notebook through a tunnel, which tends to drop.

- Kaggle sessions have time and weekly GPU quota limits. Check the current ones and plan test runs accordingly. Don’t waste GPU hours on debugging code that could run on CPU.

- Persist outputs from /kaggle/working to the backend storage before the session ends.

- treat kaggle as a backend server that uses the FastAPI server; you can send requests to process and receive from it the results

- to expose the Kaggle server, use Cloudflare so it become from localhost to a real URL

### 4.4 Backend (free and simple)

- Suggested stack: FastAPI (or any framework the team knows) plus SQLite or Postgres.

- Suggested minimum data model: User, Project, Task(type, status, stage, progress, error, created_at), plus file paths for the video, frames, poses, and splat.

- Suggested endpoints:

- POST /auth/signup, POST /auth/login (bonus / optional, not needed)

- POST /projects, GET /projects (user project not global)

- POST /projects/{id}/video

- POST /projects/{id}/reconstruct

- GET /tasks/{id} (returns status, stage, progress 0–100, error)

- GET /projects/{id}/scene (returns the splat file URL and metadata)

- The progress bar must show real stages (extracting frames, estimating poses, training, exporting), not a fake timer. Have the worker report progress to POST /tasks/{id}/progress.



### 4.5 Frontend and viewer

- Keep the UI plain. Pages needed: login/sign-up, projects list, upload with submit, progress page, viewer page.

- Viewer: research existing open-source web Gaussian splat viewers (three.js based or standalone) and integrate one. Required controls: orbit and free fly (WASD plus mouse), with sensible speed.

- Fallback if splat rendering fails: render the sparse point cloud in three.js and mark this as a known limitation.

- Leave room for Week 2: the viewer should expose a hook for “user clicked at screen position (x, y)” and be able to load a camera path or a specific camera pose.
